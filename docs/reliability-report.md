## Architecture and ownership after the changes

`Application` owns the manager, window, portal, indicator, and update checker, and stops them from `GApplication.shutdown`. `MprisManager` owns a persistent registry keyed by well-known MPRIS names. Each `MprisPlayer` and transport belongs to one **unique D-Bus owner**. Replacing or losing that owner stops the old model, unsubscribes its signals, and cancels its work before it can publish another result.

Discovery subscribes before taking its initial snapshot and rejects owner lookups overtaken by ownership events. Presence and readiness are separate: an unavailable player remains discoverable, while controls and automatic selection require a successful Player snapshot. Automatic selection retains Playing → Paused → other priority and registry order for ties. Manual selection survives an atomic owner replacement; controls wait for the replacement to initialize. A name disappearing clears the pin and permits fallback.

Property signals update cached state. In-flight snapshots merge newer deltas, honor invalidations, and clear omitted optional values. Position uses `Seeked`, monotonic time, and Rate, with asynchronous samples at transitions and when the window becomes visible. The visible progress timer performs no D-Bus polling. The active model alone fetches queue metadata, with one cancellable refresh sequence and batches of 64.

The window and indicator consume cached models. Controls check capabilities in the model, preserve remote errors, and read back state. Seek and property-write bursts coalesce; accumulated volume-wheel steps are preserved. Volume views use the latest pending request until it settles, while the model's confirmed volume remains separate. `ArtworkLoader` owns artwork requests, retries, and its file monitor. The window retains only the current decoded image and texture. No historical artwork cache was introduced.

## PR review follow-up

[The volume feedback finding](https://github.com/ChrisLauinger77/mpris-miniplayer/pull/33#discussion_r3940935920) is P2, confirmed with high confidence. Holding a Volume write reproduced a 75% request still displayed as 55%; releasing the window slider read that same stale confirmed value. The model now exposes `display_volume` for pending intent and emits changes when the request is queued or settled. Slider, mute, menu, and temporary tray feedback use this value; actual player state remains in `volume`. Clamped values, failed operations, and newer signals restore authoritative feedback, and shutdown clears pending intent. The tray's feedback subscription is disconnected on player changes and shutdown.

Five additional regressions cover menu feedback, delayed/coalesced writes and readback, write/read failures during recovery, newer volume signals, and reentrant shutdown. The menu regression failed before the fix and passes afterward. No translated strings changed. Actual pointer interaction and live status-watcher rendering remain part of desktop validation.

## Remaining decisions and limits

1. **Flatpak access:** choose the supported host-file artwork contract and whether to replace unrestricted session-bus access with filtered MPRIS access. Test the unique-owner transport through the resulting D-Bus proxy policy before changing permissions.
2. **Selection UX:** persistent cross-session pins, duplicate player-name disambiguation, and different automatic tie-breaking policies remain product choices. Current selection remains session-local.
3. **Queue scale:** full queues are preserved, so active-queue memory still scales with queue size. Pagination, truncation, or a hard cap would change current behavior and needs a product limit.
4. **Artwork freshness:** a successful HTTP URL whose contents change without any metadata change provides no event to observe. A TTL or explicit refresh control would be a product choice; bounded failure retries and track/file changes are handled.
5. **Reproducibility:** exact container/SDK commits, dependency snapshots, retained build provenance, and byte-for-byte comparisons require a defined release-reproducibility target. Fedora 44 is an explicit released baseline, not a claim that its package repository is frozen ([release announcement](https://fedoramagazine.org/announcing-fedora-linux-44/)).

Calls already delivered to a player cannot be recalled. With a valid track ID, SetPosition carries the server-side track guard. Players without one retain the existing relative Seek fallback, whose protocol cannot guard against a server changing tracks during delivery. Actual compositor focus/minimization behavior, decoder-backend behavior, HTTP artwork recovery, portal permissions, and watcher interoperability remain platform tests.

Implementation proceeded in dependency order: parsing and leak fixes; owner registry and asynchronous transport; state/queue/control synchronization; artwork and application cleanup; desktop integration; then regression and release gates. The remaining release order is full CI, package/upgrade tests, and the desktop matrix above.
